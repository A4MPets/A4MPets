Rutas API y controladores Laravel

1. ¿Dónde se declaran los endpoints HTTP principales del backend?

En backend/routes/api.php. Ahí se agrupan rutas por prefijos como auth, hazards, pets, routes, lost-pet-reports, found-pet-reports y generic-reports.

2. ¿Por qué se usa Route::prefix('hazards')?

Para agrupar todas las operaciones de peligros bajo una misma raíz REST: listado, creación, detalle, comentarios, edición y eliminación. Esto mejora legibilidad y mantiene una convención de recursos.

3. ¿Qué diferencia hay entre GET /api/hazards y GET /api/hazards/{hazardReport}?

index devuelve una lista paginada y formatea peligros sin comentarios completos por eficiencia. show carga relaciones y devuelve el detalle del peligro seleccionado.

4. ¿Cómo funciona el route model binding en {hazardReport}?

Laravel resuelve automáticamente el parámetro de ruta contra el modelo HazardReport. Si el ID no existe, responde 404 sin que el controlador tenga que buscarlo manualmente.

5. ¿Qué método del controlador crea un peligro?

HazardReportController::store. Recibe un StoreHazardRequest, pasa datos validados a HazardReportService::store y responde 201 con el peligro formateado.

6. ¿Por qué store recibe $request->user()?->id?

Porque la creación de peligros soporta usuario opcional. Si hay token válido, se asocia el reporte al usuario; si no, puede quedar como anónimo dependiendo de la ruta y middleware.

7. ¿Qué hace HazardReportController::comments?

Carga comentarios y usuario asociado, luego transforma cada comentario con ReportCommentFormatter::formatComment. Devuelve un arreglo limpio en data.

8. ¿Qué hace HazardReportController::storeComment?

Valida el payload con StoreReportCommentRequest y llama a ReportCommentService::storeComment pasando el modelo de peligro, el usuario resuelto y los datos validados.

9. ¿Por qué el endpoint de comentarios de peligros usa api.token sin :required?

Porque permite comentarios anónimos si no hay token, pero si el token existe el middleware resuelve el usuario y el comentario queda asociado a ese usuario.

10. ¿Qué endpoint requiere token obligatorio para rutas guardadas?

GET /api/routes usa api.token:required, porque las rutas guardadas son datos privados de una cuenta.

11. ¿Qué método maneja planificación de rutas?

RoutePlanningController::plan. Valida puntos, filtros y modo de viaje, invoca GraphHopperRoutingService::planRoute y devuelve coordenadas, distancia, duración e instrucciones.

12. ¿Por qué RoutePlanningController::plan devuelve 502 al fallar?

Porque el fallo suele depender de un servicio externo o de integración con GraphHopper. Un 502 expresa que el backend no pudo completar la operación por dependencia aguas abajo.

13. ¿Dónde se valida que una ruta planificada tenga mínimo dos puntos?

En RoutePlanningController::plan, con la regla 'points' => 'required|array|min:2'.

14. ¿Cómo se restringen coordenadas inválidas en planificación?

Con reglas de validación: latitud entre -90 y 90, longitud entre -180 y 180. Eso evita enviar coordenadas absurdas a GraphHopper.

15. ¿Qué ventaja tiene usar controladores pequeños?

El controlador se enfoca en HTTP, validación y respuesta. La lógica compleja queda en servicios, lo que facilita pruebas unitarias y mantenimiento.

Middleware, autenticación y permisos

16. ¿Qué clase resuelve el usuario desde un token API?

App\Http\Middleware\ResolveApiTokenUser. Lee el bearer token, calcula su SHA-256, busca el registro ApiToken y establece el usuario autenticado en Laravel.

17. ¿Por qué se calcula hash('sha256', $bearerToken)?

Porque en base de datos se guarda el hash del token, no el token plano. Esto reduce impacto si la base se expone accidentalmente.

18. ¿Cómo se maneja expiración de tokens?

El middleware verifica que expires_at sea nulo o futuro. Si el token expiró, no establece usuario.

19. ¿Qué hace Auth::setUser($user) en el middleware?

Registra el usuario autenticado en el contexto actual de Laravel, de modo que $request->user() funcione en controladores y FormRequests.

20. ¿Para qué sirve el parámetro $mode = 'optional'?

Permite reutilizar el middleware en dos modos: opcional, donde el usuario se resuelve si hay token, y requerido, donde se devuelve 401 si no se resolvió usuario.

21. ¿Qué diferencia concreta hay entre api.token y api.token:required?

api.token permite continuar sin usuario; api.token:required bloquea la petición con 401 si no existe un token válido.

22. ¿Dónde se actualiza last_used_at del token?

En ResolveApiTokenUser, cuando encuentra un token válido. Se usa forceFill y save para registrar uso reciente.

23. ¿Por qué las rutas de edición y eliminación están en un grupo con token requerido?

Porque modifican datos persistidos y deben estar asociadas a una identidad. Luego los servicios aplican reglas de propiedad o permiso.

24. ¿Dónde se decide si un usuario puede actualizar un peligro?

En HazardReportService::canMutate, llamado desde HazardReportController::update antes de aplicar cambios.

25. ¿Qué respuesta se devuelve si un usuario no puede mutar un peligro?

El controlador devuelve JSON con success=false, mensaje No autorizado y código HTTP 403.

26. ¿Por qué no basta con verificar permisos en Flutter?

Porque un atacante podría llamar la API directamente. La autorización real debe ejecutarse en Laravel, no solo ocultando botones en la interfaz.

27. ¿Cómo se conserva el modelo de usuario en la petición?

El middleware define $request->setUserResolver(static fn () => $user), por eso los controladores pueden usar $request->user().

28. ¿Qué mejora haría a seguridad de tokens?

Agregar rate limiting, rotación/revocación granular, scopes por token, expiraciones cortas configurables y auditoría de accesos fallidos.

Modelos Eloquent y persistencia

29. ¿Qué campos permite asignar masivamente HazardReport?

Los definidos en $fillable: coordenadas, radio, catálogos, descripción, fechas, usuario, estado, IDs local/remoto y timestamps de sincronización.

30. ¿Para qué sirve $casts en HazardReport?

Convierte valores a tipos esperados: floats para coordenadas/radio, enteros para IDs y objetos fecha para campos temporales.

31. ¿Qué hace $appends en HazardReport?

Agrega atributos calculados al JSON: risk_level_code, category_code, estimated_duration_code y comments_json.

32. ¿Cómo se obtiene risk_level_code?

Con el accessor getRiskLevelCodeAttribute, leyendo la relación riskLevel y devolviendo su code, o undefined como fallback.

33. ¿Qué hace setRiskLevelCodeAttribute?

Normaliza el código recibido y traduce el código al risk_level_id usando HazardRiskLevel::idByCode.

34. ¿Por qué setCategoryCodeAttribute transforma aggressive_animals?

Mantiene compatibilidad con una categoría anterior, migrándola a possible_rabies_vectors. Es una decisión de normalización de dominio.

35. ¿Qué relación define HazardReport::comments()?

Una relación MorphMany hacia ReportComment, ordenada por commented_at y luego por id.

36. ¿Qué devuelve getCommentsJsonAttribute?

Un JSON con autor, avatar, anonimato, texto y fecha en milisegundos. Sirve para que el frontend pueda reconstruir comentarios en sus modelos.

37. ¿Qué hace scopeNearby?

Filtra peligros dentro de un rango aproximado usando deltas de latitud/longitud. Es una aproximación simple, no una consulta geoespacial exacta.

38. ¿Por qué scopeNearby no reemplaza PostGIS?

Porque usa grados aproximados y no índices espaciales reales. PostGIS permitiría distancias y geometrías más precisas y eficientes.

39. ¿Qué hace resolvesConflictWith?

Implementa una regla last write wins: gana el peligro con last_modified_at más reciente o igual.

40. ¿Qué modelo representa comentarios unificados?

ReportComment. Incluye commentable_type, commentable_id, autor, anonimato, texto, fecha y hash de contenido.

41. ¿Qué relación define ReportComment::commentable()?

Una relación MorphTo, que permite que un comentario pertenezca a un peligro, reporte perdido, reporte encontrado o reporte genérico.

42. ¿Qué hace ReportComment::makeContentHash?

Genera un SHA-256 usando tipo, ID, usuario, autor, avatar, anonimato, texto y timestamp normalizado. Se usa para deduplicación.

43. ¿Por qué se normaliza el timestamp a segundos en el hash?

Para evitar que diferencias de milisegundos generen hashes distintos para comentarios equivalentes recibidos desde distintas fuentes.

44. ¿Qué problema resuelve fillable?

Evita asignación masiva de campos no permitidos. Solo los atributos definidos pueden llenarse mediante métodos como create o update.

Servicios de dominio y comentarios

45. ¿Por qué existe ReportCommentService?

Centraliza creación, sincronización, deduplicación y normalización de comentarios. Así los controladores no duplican reglas.

46. ¿Qué hace storeComment en ReportCommentService?

Determina autor/anonimato, parsea fecha, arma payload polimórfico, genera hash y usa updateOrCreate para persistir.

47. ¿Cuándo se guarda user_id en un comentario?

Solo si existe usuario y el comentario no es anónimo. Si no hay usuario o se marca anónimo, user_id queda nulo.

48. ¿Qué valor toma author_name si no se envía?

Si hay usuario y no es anónimo, usa el nombre del usuario. Si no, usa Anonimo.

49. ¿Qué hace syncComments?

Recorre comentarios recibidos, descarta entradas inválidas o vacías, normaliza autor y fecha, detecta existentes por hash o equivalencia, crea o actualiza y luego poda duplicados.

50. ¿Qué hace findEquivalentComment?

Busca un comentario con mismo tipo, ID, autor, anonimato, texto, usuario y fecha dentro del mismo segundo. Sirve como segunda barrera contra duplicados.

51. ¿Por qué pruneDuplicateComments construye una clave compuesta?

Para detectar duplicados por datos semánticos del comentario aunque existan IDs o hashes diferentes por sincronizaciones anteriores.

52. ¿Qué método parsea fechas en comentarios?

parseCommentTimestamp. Acepta Carbon, enteros/milisegundos, strings numéricos y strings parseables por Carbon.

53. ¿Qué riesgo hay en usar Carbon::parse con strings libres?

Puede aceptar formatos ambiguos. En producción convendría exigir ISO 8601 o timestamp controlado para reducir interpretaciones inesperadas.

54. ¿Qué clase formatea comentarios para la API?

ReportCommentFormatter, que expone campos como ID, tipo, usuario, autor, avatar, anonimato, texto y fecha ISO.

GraphHopperRoutingService e implementación de rutas

55. ¿Qué clase encapsula la comunicación con GraphHopper?

App\Services\GraphHopperRoutingService. Construye payload, maneja perfiles, filtros de peligro, fallback de URLs, timeouts y respuesta de ruta.

56. ¿Qué hace resolveBaseUrls?

Construye una lista de URLs posibles: la configurada, http://graphhopper:8989 para Docker y http://127.0.0.1:8989 para local, evitando duplicados.

57. ¿Por qué hay fallback entre varias URLs de GraphHopper?

Porque el sistema puede ejecutarse en Docker o local. El fallback aumenta tolerancia cuando cambia el entorno de ejecución.

58. ¿Qué timeout usa la petición a GraphHopper?

Usa Http::timeout(20), lo que evita que Laravel quede esperando indefinidamente si GraphHopper no responde.

59. ¿Cómo se convierten puntos del frontend al formato de GraphHopper?

El backend recibe lat y lng, pero GraphHopper espera pares [lng, lat]. buildPayload hace esa conversión.

60. ¿Por qué se envía points_encoded=false?

Para recibir coordenadas explícitas en JSON en lugar de una polilínea codificada. Eso simplifica consumo desde Flutter.

61. ¿Qué hace mapTravelModeToProfiles?

Mapea valores como walking o foot al perfil foot, y valores como car o driving al perfil car.

62. ¿Qué ocurre si el modo de viaje no es reconocido?

El servicio usa car como fallback. Es una decisión conservadora, aunque podría validarse más estrictamente.

63. ¿Por qué se agrega ch.disable=true al evitar peligros?

Porque el custom_model de GraphHopper no es compatible con speed mode basado en Contraction Hierarchies. Desactivarlo permite aplicar reglas personalizadas.

64. ¿Cómo se limita la consulta de peligros considerados para rutas?

Se calcula un bounding box alrededor de los puntos con routeBounds y se consulta solo peligros dentro de ese rango, con límite de 100.

65. ¿Qué hace buildCirclePolygon?

Genera un polígono aproximado circular alrededor de una coordenada usando radio terrestre y segmentos. Ese polígono se usa como área de evitación.

66. ¿Por qué el radio se calcula con impact_radius_meters + 25 y mínimo 25?

Agrega margen de seguridad y evita áreas de evitación demasiado pequeñas para que el motor de rutas pueda considerarlas.

67. ¿Qué se devuelve si GraphHopper responde sin paths?

Se registra el intento como sin paths y se prueba otra combinación de perfil/URL. Si todas fallan, se lanza RuntimeException.

68. ¿Qué clase normaliza instrucciones de navegación?

NavigationInstructionFormatter, invocada desde GraphHopperRoutingService para convertir instrucciones del motor al formato usado por la app.

Frontend: cliente HTTP, repositorio y providers

69. ¿Qué clase centraliza llamadas HTTP en Flutter?

BackendApiClient. Expone métodos getWithFallback, postWithFallback, putWithFallback y deleteWithFallback.

70. ¿Cómo obtiene el frontend la URL base de API?

Usa String.fromEnvironment('A4M_API_BASE_URL') con valor por defecto http://localhost:8000/api, además de fallbacks locales.

71. ¿Para qué sirve BackendApiClient.workingBaseUrl?

Recuerda la última URL que funcionó, para intentar primero esa base en peticiones futuras y reducir fallos de conexión en entornos variables.

72. ¿Por qué baseUrls incluye 10.0.2.2 solo cuando no es web?

Porque 10.0.2.2 es el alias del host desde emulador Android. En web no aplica.

73. ¿Qué hace jsonHeaders?

Construye headers Content-Type, Accept y, si existe token, Authorization: Bearer ....

74. ¿Por qué los métodos con fallback retornan errores 4xx inmediatamente?

Porque un 4xx indica problema de cliente o permisos, no de disponibilidad del servidor. No tiene sentido probar otra URL si el contrato respondió.

75. ¿Qué clase abstrae operaciones de usuario y datos en Flutter?

UserLocalRepository. Coordina SessionStore, GuestDataStore y BackendApiClient.

76. ¿Qué hace getUserProfile cuando falla /auth/me?

Devuelve el perfil cacheado. Así evita cerrar abruptamente la sesión visual por una falla temporal de red.

77. ¿Qué ocurre después de registrar usuario?

register guarda el perfil autenticado, migra mascotas y rutas invitadas a la cuenta y luego limpia datos de invitado.

78. ¿Qué hace _requireToken?

Lee el perfil local y lanza excepción si no hay usuario autenticado con token. Se usa para acciones privadas.

79. ¿Por qué addCommentToHazard no exige token?

Porque los comentarios de peligros pueden ser anónimos. Si hay sesión, envía token; si no, envía comentario sin autorización.

80. ¿Qué hace _normalizeMap?

Convierte booleans a 0/1, fechas ISO a milisegundos, transforma listas comments en comments_json y agrega defaults de sincronización.

81. ¿Qué riesgo introduce convertir booleans a 0/1?

Los modelos Dart deben aceptar ambos formatos. Por eso ReportCommentRecord parsea is_anonymous como bool, número o texto.

82. ¿Qué provider controla la lista de peligros?

hazardReportsControllerProvider, definido como AsyncNotifierProvider y respaldado por HazardReportsController.

83. ¿Por qué HazardReportsController extiende AsyncListController?

Para reutilizar lógica de carga, recarga y refresco periódico de listas asíncronas. En peligros define intervalo de 60 segundos.

84. ¿Qué hace addHazardReport en el provider?

Llama al repositorio para crear el peligro y luego ejecuta reload(), de modo que la UI vea datos actualizados.

Modelos Dart, parseo y serialización

85. ¿Qué modelo Dart representa un peligro?

HazardReportRecord. Contiene ID, UUID local, estado, coordenadas, radio, categoría, descripción, duración, riesgo, foto, autor, comentarios y fechas.

86. ¿Cómo parsea comentarios HazardReportRecord?

Lee comments_json, lo decodifica con jsonDecode y transforma cada elemento en HazardCommentRecord, alias de ReportCommentRecord.

87. ¿Qué fallback usa HazardReportRecord si no hay local_uuid?

Genera un identificador tipo legacy-{id} o basado en tiempo, para mantener compatibilidad con registros antiguos.

88. ¿Qué hace ReportCommentRecord._parseCreatedAt?

Acepta milisegundos numéricos, strings numéricos o strings ISO. Si no puede parsear, usa DateTime.now().

89. ¿Qué hace ReportCommentRecord._parseBool?

Acepta bool, número o texto como true, false, 1, 0, yes, no, si o sí. Evita fallos por diferencias de formato.

90. ¿Por qué los modelos tienen toMap?

Para serializar datos hacia almacenamiento local, pruebas o payloads internos. Mantiene simetría parcial con fromMap.

91. ¿Qué hacen los métodos de etiquetas como riskLabelFromCode?

Traducen códigos técnicos como low, medium o high a textos de UI como Bajo, Medio y Alto.

Docker, ejecución y configuración

92. ¿Qué instala el backend/Dockerfile?

Parte de php:8.4-cli, instala dependencias como git, unzip, curl, SQLite dev y compila pdo_sqlite. También copia vendor desde una etapa Composer.

93. ¿Por qué el Dockerfile usa una etapa composer:2 AS vendor?

Para instalar dependencias PHP en una etapa separada y copiar vendor al contenedor final, simplificando el runtime.

94. ¿Qué hace a4mpets-media.ini en el Dockerfile?

Configura post_max_size = 0 y upload_max_filesize = 0. Es una decisión específica para manejo de medios, aunque debería revisarse para producción.

95. ¿Qué valida backend/docker/entrypoint.sh antes de arrancar?

Verifica que APP_KEY exista. Si la base es SQLite, crea el archivo, luego ejecuta migraciones y arranca php artisan serve.

96. ¿Qué riesgo hay en ejecutar migraciones automáticamente al arrancar?

En producción puede aplicar cambios no deseados durante despliegue. Lo ideal es un pipeline controlado con backup y revisión previa.

97. ¿Qué servicio de Docker provee ruteo?

graphhopper, definido en docker-compose.yml. Monta el mapa PBF, la configuración y un volumen de cache de grafo.

Pruebas y validación técnica

98. ¿Qué prueba backend cubre comentarios anónimos de peligro?

HazardControllerExtraTest::test_guest_can_add_anonymous_hazard_comment. Verifica POST sin token, autor Anonimo, user_id nulo y consulta posterior.

99. ¿Qué prueba frontend cubre el parseo flexible de is_anonymous?

En frontend/test/models/report_records_extra_test.dart, una prueba valida que ReportCommentRecord.fromMap acepte anonimato como entero o texto.

100. Si el jurado pide demostrar que la implementación es verificable, ¿qué comandos mostraría?

Mostraría php artisan test o filtros de PHPUnit para backend, flutter test para modelos/providers/widgets, npm run test:e2e:f5 para Playwright y pruebas HTTP reales contra endpoints como /api/health, /api/hazards y /api/routes/plan.

Nota para sustentación técnica

En defensa de código, conviene responder mencionando archivo, clase y método. Una respuesta fuerte no solo dice “funciona”, sino “funciona porque esta ruta llama a este controlador, este controlador delega en este servicio, este modelo persiste estos campos, y esta prueba lo verifica”.
